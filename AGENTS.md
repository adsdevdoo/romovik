# ROMовик

- Порядок каталога — **всегда по добавлению, новый в конце** (прямое указание владельца 22.11.2026). Постоянный `sequence` назначается при импорте как максимальный существующий + 1; при уточнении описания/фото не меняется. Не сортировать по имени, размеру или одной только дате и не возвращать выбор сортировки. Поиск/фильтры сохраняют порядок и номера. Проверять порядок на главной странице, включая последнюю запись; отдельная карточка не подтверждает правильный порядок списка.

- Публичный репозиторий. Секреты, локальные пути владельца и серверные конфиги сюда не добавлять.
- По решению владельца 22.11.2026 надпись «Часть creepypaste» удалена из подвала; не возвращать её.
- Продукт: ROMовик (Romovik), адрес https://rom.creepypaste.rs. Новое решение владельца 22.11.2026: MongoDB, форма отправки и модерация с отдельной учётной записью ROMовика (без SSO). Astro + Tailwind рендерят HTML на сервере; Java/Javalin использует helpers MongoDatabaseManager и PasswordHasherHelper. Это заменяет прежнее решение о статике без базы.
- Дампы/фотографии владелец передаёт в чат для публикации. Бинарники и фото остаются вне Git в archive/, метаданные — catalog/*.json. Изменение байтов недопустимо.
- Модель и производитель — по фотографии и подтверждённым данным, а не опечаткам в имени файла. Неизвестное происхождение сохранять как неизвестное. Текст внутри файла — свидетельство содержимого, а не доказательство модели устройства.
- Замечания о нечитаемых надписях сообщать владельцу в чате и сохранять в рабочих заметках; не выводить на публичном сайте фразы вроде «Полная маркировка на фотографии неразборчива» (указание владельца 22.11.2026). Это не отменяет ожидания уточнений перед добавлением новых экземпляров. Недостающие надписи не выдумывать.
- Импорт, извлечение строк и проверки — README.md. npm test, npm run build, npm run check:dist перед выпуском; проверить затронутый сценарий в браузере. Не запускать проверки других проектов.
- Сборка для публикации — из конкретного коммита, с отдельно проверенными archive/. Два образа web/API, отдельный nginx; развёртывание, секреты, резервное копирование и серверные адреса — только в частном инфраструктурном репозитории владельца. Для новой серверной конфигурации нужен независимый аудит до выкатки.
- Заметки, договорённости, проверки и выпуски записывать в docs/NOTES.txt. Идеи на потом — docs/BACKLOG.md с датой и источником. Коммитить только свои файлы; до коммита и push сверять origin и status.

## Добавление из чата — постоянный порядок (решение владельца 22.11.2026)

Полученный в этом проекте дамп с фотографией означает просьбу добавить микросхему в каталог и опубликовать её на сайте после проверки читаемости маркировки. Владелец может присылать следующие файлы во время работы. Обработать все полученные файлы, не требовать повторять поручение или отдельно подтверждать каждую публикацию, когда маркировка прочитана или уточнена владельцем. Если что-либо на корпусе не читается, немедленно сообщить об этом и ждать уточнения: до ответа владельца такую микросхему не добавлять и не публиковать. Описание необязательно. Отсутствие происхождения или ошибка Check ID не задерживают добавление; диагностику продолжать только по отдельной просьбе.

1. Прочитать эти инструкции, README.md и docs/NOTES.txt, проверить состояние Git и origin. Составить соответствие «точное имя исходного файла → SHA-256 → карточка → фотография». Различать файлы без суффикса и с `-2`, `-3`; не принимать их автоматически за повторные чтения одного экземпляра. Не импортировать соседние файлы, которые владелец не присылал. До импорта проверить все надписи на корпусе. Если какая-либо часть неразборчива, сразу указать владельцу точное имя дампа и конкретную неразборчивую часть; остановить добавление этого экземпляра до нового фото или текстового уточнения от владельца.
2. Импортировать через `scripts/add-dump.mjs` по README. Сохранить исходные байты и фотографии в `archive/`, размер и SHA-256 в метаданных. `dump.originalFilename` хранит точное имя без локального пути и показывается в карточке/поиске. Совпадение SHA-256 с другой карточкой сообщить, но отдельный физический экземпляр не удалять. Постоянный id: модель и различимый код экземпляра; если кода нет — короткий SHA-256. Уже опубликованный id сохранять при уточнениях.
3. Модель, производитель и маркировка — по фото и подтверждённым данным. Имя файла связывает вложения, но может содержать опечатку или только профиль программатора: оно не заменяет уточнение нечитаемой надписи. Владелец может написать маркировку текстом вместо нового фото; перенести её точно, указать источник уточнения и не требовать пересъёмку. Не придумывать суффикс или код партии. Неизвестное устройство и плату оставлять неизвестными. При исправлении фото владельцем обновить только указанную карточку, сверить хеш нового изображения; ошибочное фото исключить из публикации, сохранив локальную историю.
4. Выполнить `scripts/inspect-dump.mjs`, вручную отобрать содержательные строки: названия, версии, идентификаторы, диагностические сообщения. Записать точные байтовые смещения и текст в `strings`, выставить `stringsReviewed`. Не публиковать случайный бинарный мусор и сотни повторов. Находки входят в HTML и поиск, но не доказывают происхождение устройства. Если ASCII-находок нет, так и указать, не утверждая отсутствия текста в других кодировках/графике.
5. Записать только наблюдаемые результаты ID и чтения. Скриншот ID относится к той карточке, вместе с которой его прислали; не переносить на следующий чип той же модели. Два ответа ID не являются двумя чтениями дампа. Совпадение повторных чтений отмечать только после побайтного сравнения файлов; работоспособность в устройстве — только при подтверждении владельцем.
6. Сверить исходники с archive/ по размеру/SHA-256. До следующего импорта синхронизировать публичный каталог с MongoDB через `npm run sync-catalog`, восстановить опубликованные вложения `fetch-assets`. Локальный sequence предварительный: авторитетный номер назначает серверная команда `import <record.json>` атомарно из MongoDB. После импорта снова синхронизировать снимок и сверить фактический номер. `seed` — только первоначальная миграция; существующие записи `import` не перезаписывает. Выполнить `npm test`, `npm run build`, `CHECK_URL=<проверяемый сайт> npm run check:dist`, затронутый сценарий в браузере. Изменения Java требуют Maven tests; изменения auth/moderation — интеграционных тестов на отдельной MongoDB. Коммитить только свои файлы. Выпуск — по deploy/romovik/README.md в частном infra; общий proxy не пересоздавать. Проверить публичные карточки, скачивания, хеши и порядок до сообщения об успехе.
7. Записать соответствие исходных имён карточкам, исправления, проверки, коммит и результат выпуска в docs/NOTES.txt; серверные пути и откат — в частном инфраструктурном репозитории. В ответе дать ссылки на опубликованные карточки и общее число добавленных дампов. Не объявлять публикацию завершённой до проверки сайта.

Обязательное ожидание при нечитаемой маркировке (прямое уточнение владельца 22.11.2026): если не читается хотя бы часть надписей — модель, суффикс, производитель или любой код на корпусе — немедленно сообщить точное имя дампа и что именно не удалось прочитать. Владелец сам выбирает: переснять фото или написать надпись текстом. До его уточнения не запускать импорт, не создавать запись в catalog/ и не публиковать этот экземпляр даже с пометкой «неразборчиво». Ожидание записать в docs/NOTES.txt с точным именем файла. После получения читаемого фото или текста продолжить обычное добавление без повторного запроса разрешения. Более чёткое фото того же экземпляра ставить первым, сохранять постоянный id и байты дампа; прежний корректный общий вид можно оставить дополнительным фото.
